# /approve-spec

Accept the implementation and archive the spec.

## Usage

```
/approve-spec @2025-11-29-stripe-integration
/approve-spec @2025-11-29-stripe-integration "Great work!"
```

## Prerequisites

- Validation must be complete
- `validation.md` must show all checks passed
- `handoff.md` must exist (generated by Arbiter)
- **TDD compliance verified** (tasks.md shows test coverage)

---

## TDD COMPLIANCE REQUIRED

```
  Before approving, verify TDD was followed:

  - [ ] tasks.md shows tests for all tasks
  - [ ] validation.md confirms TDD compliance
  - [ ] All tests pass

  DO NOT APPROVE if TDD was skipped
```

---

## Workflow

### Phase 1: Final Verification

1. **TDD Compliance Check:**
   - Read `tasks.md` Progress section
   - Verify tests were written first
   - Check `validation.md` shows TDD compliance

2. **Validation Check:**
   - Verify all validation checks passed
   - Review `handoff.md` for completeness

3. **User Review:**
   - Check user has reviewed
   - Note any user feedback

**If TDD was not followed:**
```
APPROVAL BLOCKED

TDD compliance not verified. Cannot approve.

Action: Return to /build-spec and follow TDD process.
        Then /validate-spec, then /approve-spec.
```

### Phase 2: Load Project Configuration

Read `.catalyst/main/project-config.yaml` to get:
- `git.protected_branches` - branches that require new branch creation
- `git.branch_prefix` - prefix for new branches (e.g., "feat")
- `repository_type` - "monorepo" or "multi-repo"
- `repositories` - list of repo paths (if multi-repo)
- `specs.completed_path` - where to archive specs

### Phase 3: Detect Changed Repositories

**If `repository_type: "multi-repo"`:**

1. **Check each repo (from config) for changes:**
   ```bash
   # For each repo in config.repositories
   cd <repo.path> && git status --porcelain
   ```

2. **List repos with changes** and show to user:
   ```
   Repositories with changes:
   - <repo.name> (X files changed)
   - <repo.name> (Y files changed)
   ```

**If `repository_type: "monorepo"`:**
- Check root directory only
- Skip multi-repo logic

### Phase 4: Branch Management (Per Repository)

For **each repository with changes**:

1. **Check Current Branch:**
   ```bash
   cd <repo.path> && git branch --show-current
   ```

2. **If on a protected branch (from `config.git.protected_branches`):**
   - Generate a suggested branch name based on spec:
     - Format: `<config.git.branch_prefix>/<spec-name-kebab-case>`
     - Example: `feat/google-drive-project-integration`

   - **Ask user ONCE using AskUserQuestion tool:**
     - Question: "Which branch name would you like to use? (Will be applied to all repos)"
     - Option 1: Generated suggestion (recommended)
     - Option 2: Free text input for custom branch name

   - **Create the branch in each repo with changes:**
     ```bash
     cd <repo.path> && git checkout -b <selected-branch-name>
     ```

3. **If already on a feature branch:**
   - Skip branch creation
   - Continue to Phase 5

### Phase 5: Git Commit (Per Repository)

For **each repository with changes**:

1. **Stage changes:**
   ```bash
   cd <repo.path> && git add .
   ```

2. **Create structured commit message with TDD stats:**
   ```
   feat(<scope>): implement <feature-name>

   TDD Compliance: Verified
   - Tests written first
   - All tests pass

   Implementation:
   - <key changes from handoff.md>

   Spec: <spec-name>
   Tests: <X> passing
   ```

3. **Commit to each repo:**
   ```bash
   cd <repo.path> && git commit -m "<commit-message>"
   ```

   Note: Same commit message used across all repos for traceability.

### Phase 6: Archive Spec

Move spec to completed (using `config.specs.completed_path`):
```
<config.specs.active_path>/<spec-name>/
-> <config.specs.completed_path>/<spec-name>/
```

Update `spec.md` status:
```markdown
> Status: COMPLETE
> Completed: YYYY-MM-DD
> Commit: abc123
```

---

### Phase 7: Library Extraction (Optional)

Extract reusable patterns into the knowledge library for future projects.

#### Step 1: Determine Applicability

**Auto-detect common patterns** from spec name/content:

| Pattern Keywords | Suggested Library Item |
|------------------|----------------------|
| `stripe`, `payment`, `billing`, `subscription` | `payment-integration.md` |
| `auth`, `oauth`, `login`, `sso`, `jwt` | `authentication.md` |
| `upload`, `s3`, `storage`, `file` | `file-storage.md` |
| `websocket`, `realtime`, `socket` | `real-time-communication.md` |
| `email`, `notification`, `smtp` | `notifications.md` |
| `search`, `elasticsearch`, `algolia` | `search-implementation.md` |
| `cache`, `redis` | `caching-strategy.md` |
| `queue`, `job`, `worker`, `bull` | `background-jobs.md` |

**Ask user using AskUserQuestion:**

```
"Should this spec be added to the pattern library for future projects?"

Options:
- Yes, create new: <suggested-name> (Recommended if pattern detected)
- Yes, update existing: [list existing library items]
- No, too project-specific (skip)
```

#### Step 2: Extract to Library (If Yes)

**Delegate to Scribe agent:**

```
"Extract reusable pattern from completed spec into library item.

Source: .catalyst/specs/completed/<spec-name>/
Target: .catalyst/library/<pattern-name>.md

CRITICAL:
- Remove ALL project-specific details (company names, specific endpoints, etc.)
- Keep generic guidelines and considerations
- Focus on: key considerations, common pitfalls, architecture patterns, testing strategy
- This should help ANY project implementing this pattern

Use the library item template format."
```

#### Step 3: Update Library Item

Scribe creates/updates `.catalyst/library/<pattern-name>.md`:

```markdown
# <Pattern Name>

> Category: <category>
> Complexity: Low | Medium | High
> Last Updated: YYYY-MM-DD
> Based on: N implementations

## Overview
Brief description of what this pattern solves.

## When to Use
- Scenario 1
- Scenario 2

## Key Considerations
- [ ] Critical consideration 1
- [ ] Critical consideration 2

## Architecture Pattern
```
Component flow diagram
```

## Common Pitfalls
1. **Pitfall name** — Why it happens and how to avoid

## Dependencies
- Required packages/services
- Environment variables needed

## Testing Strategy
- How to test this pattern effectively

## Database Considerations
- Schema patterns if applicable

## Related Specs
- <spec-name-1> (YYYY-MM-DD)
- <spec-name-2> (YYYY-MM-DD)
```

**If updating existing item:**
- Append new spec to "Related Specs"
- Merge any new pitfalls/considerations discovered
- Update "Last Updated" date
- Increment implementation count
