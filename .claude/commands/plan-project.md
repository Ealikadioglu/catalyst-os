# /plan-project

Plan the future of the project: maintain `roadmap.md` as a **queue of specs grouped by lifecycle state**, with a single clear next action.

> **Companion to `/sync-project`.** `/plan-project` plans what's *not yet started* (Backlog, ordering, Next Up direction); `/sync-project` reconciles what's *already done* (archives finished specs). Plan the future, sync the past.

## Usage

```
/plan-project              # Create new or update existing
/plan-project "Q1 focus"   # Update with specific direction
```

## Core Principle

**The roadmap is a queue of specs, not a checklist of tasks.**

- One entry = one spec = one forge cycle (one PR-sized unit of work).
- Tasks belong in each spec's `tasks.md` — never in the roadmap.
- Sections are **lifecycle states**, not time horizons. A spec moves across the board as it progresses: `Backlog → Planned → In Progress → Audited → Done`.
- There is always exactly **one `▶ Next Up`** so "what's the next spec?" is answerable at a glance.

> The lifecycle and state detection are defined once in the **`spec-lifecycle-board`** skill; the board files are generated by `node .catalyst/bin/board.js`. This command owns the *planning* judgment only (waves, backlog ideas, ordering, Vision) — you edit the **🌊 Waves**, **🗂️ Backlog**, and **Vision / Someday** sections of `roadmap.md`, then run the script. You never touch Next Up, Planned, In Progress, Audited, Done, or `dashboard.html`.

## Workflow

1. **Read** `.catalyst/main/mission.md` for context
2. **Read existing** `.catalyst/main/roadmap.md` if present
3. **Scan specs** in `.catalyst/specs/` and `.catalyst/specs/completed/` to determine the state of each
4. **Analyze** codebase for current feature state
5. **Ask** about priorities and ordering:
   - What's the single most important thing next?
   - What's blocking progress?
   - In what order should the backlog be built?
6. **Order the Backlog** — it is a ranked queue by position; the top entry becomes Next Up once the board clears
7. **Group into Waves** when the work will run unattended (`/forge-wave`). See *Waves* below.
8. **Write only the Waves, Backlog, and Vision sections** of `roadmap.md` (template: `.catalyst/main/temp/temp-roadmap.md`). If the file does not exist yet, write just those sections under the template header.
9. **Run the board script** — it classifies on-disk specs, resolves `▶ Next Up`, fills the lifecycle sections, and regenerates the dashboard:

   ```bash
   node .catalyst/bin/board.js --by "/plan-project" --init
   ```

## State Detection & Next Up

Handled entirely by `board.js` (rules in the `spec-lifecycle-board` skill): five states — 🗂️ Backlog · 📋 Planned · 🔨 In Progress · 🔬 Audited · ✅ Done — detected from each spec folder's files, and Next Up = the spec closest to Done (Audited → In Progress → Planned → top of Backlog). You do not compute any of this.

## Granularity Guardrail

Before writing any entry, check its size:

- If it would need **more than ~5-8 tasks**, or spans **multiple subsystems** (e.g. backend + frontend + migrations as separable pieces), it is **too big for one spec** → split it into multiple ordered Backlog entries.
- Replace task checklists with a one-line **Scope** + a **Done when** acceptance criterion. Detailed tasks are `tasks.md`'s job, produced later by `/forge-spec`.
- Every Backlog entry gets a `Catalyze as: {slug}` hint so naming is decided up front, plus a seed prompt ready to hand to `/catalyze-spec`.

## Backlog Ordering

The Backlog is a **ranked queue** — position is the priority, the `### N.` number is a permanent ID. Reorder by moving entries; never renumber, since `Depends on: #N`, wave plans, and changelogs point at those IDs. Write new entries as `### Name` without a number and `board.js` assigns the next free ID. Mark a slugless entry finished with ✅ in its title and it moves to Done. Order by:
1. Dependencies (a spec can't precede what it depends on — note `Depends on:` per entry). Write dependencies as `Catalyze as` slugs (`Depends on: auth-accounts, order-request`): a slug still resolves after the entry graduates, and `board.js --wave` uses it to report what each spec waits on
2. Unblocking value (what makes the product usable / lets other work proceed)
3. Priority label (🔴 → 🟢)

## Waves

A wave is a group of Backlog specs that together reach one outcome, built one after another by `/forge-wave <id>`. Each spec in a wave is catalyzed against the code the specs before it merged.

```markdown
## 🌊 Waves

### Wave 1
**Goal:** Shipments are sorted, split per agency, and scanned into parcels, so the office runs dispatch end to end.

1. `shipment-sorting`
2. `agency-split`
3. `parcel-scan`
```

- **Goal:** one or two sentences in plain English, the outcome a person would notice. No feature list.
- **Specs:** the `Catalyze as` slugs of Backlog entries, numbered in build order. Order respects `Depends on`; a spec never precedes what it depends on.
- **IDs are permanent.** Never renumber a wave; add new ones after the last. A finished wave stays, showing ✅.
- **Size:** a night's work. Past roughly ten specs, split it.
- `board.js` writes the **Status** line and a state mark per spec. Do not write them yourself.

## Output Format

`.catalyst/main/roadmap.md` — uses the structure defined in `.catalyst/main/temp/temp-roadmap.md`:

- `▶ Next Up` — the single next action
- `🌊 Waves` — ordered groups of specs for `/forge-wave` (optional)
- `🗂️ Backlog` — ordered queue of not-yet-catalyzed specs
- `📋 Planned` — catalyzed, ready to forge
- `🔨 In Progress` — being built (keep to 0-1, WIP limit)
- `🔬 Audited` — validated, awaiting seal
- `✅ Done` — sealed specs, for closure and history
- `Vision / Someday` — strategic goals not yet ready to be specs

## Dashboard

`.catalyst/dashboard.html` is produced by the script call in step 8 — a whole-`.catalyst/main` control panel tabbed across **Roadmap / Mission / Tech Stack / Architecture / Concerns / Conventions**. Do not read the template or write the file yourself. Tell the user to double-click it.
